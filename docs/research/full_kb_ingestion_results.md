**Branch:** `feat/full-kb-ingestion` | **Date:** 2026-10-09
**Baseline KB (unchanged):** 24 hand-written seed entries in database `trc_engine`.
**Full KB (new, separate DB `trc_engine_fullkb`):** 2,300 entries.

## Existing benchmark re-run (same 40 labelled pairs, K=5)

| Metric | Baseline (24 seed) | Full KB (2,300) |
|---|---:|---:|
| Precision@5 | 0.5667 | 0.1667 |
| Recall@5 | 0.4286 | 0.1321 |
| Hit@5 | 83.3% | 66.7% |
| MRR | 0.7222 | 0.3667 |
| Latency P50 / P95 (this machine, today) | 54.2 / 68.7 ms | 72.6 / 84.6 ms |

The baseline row reproduces the 2026-09-19 result exactly (latency differs by machine/load).

**How to read the drop.** The labelled "relevant" patterns are IDs from the 24-entry seed KB.
With 2,300 entries, many other relevant patterns exist that are not labelled, and they count
as misses. The drop is therefore a lower bound on quality, not a like-for-like comparison.
It does show that the labelled patterns now compete with ~100x more candidates.

## What the full KB changes in practice (top results, not just scores)

Improvements:
- Secure element (SDL-Q2) now retrieves `CAPEC-624` Hardware Fault Injection, `CAPEC-440`
  Hardware Integrity Attack and `CAPEC-665`; the smart-lock key asset (AS-6) retrieves
  `CAPEC-622` Electromagnetic Side-Channel Attack and `CAPEC-624`. The seed KB had none of these.
- BLE controller (SDL-Q1) now retrieves `CAPEC-667`/`CAPEC-668` (Bluetooth-specific attacks).
- Firmware asset (AS-3) retrieves `ATT&CK-T1542.002` Component Firmware and `CWE-1277`.

Problems observed (not yet fixed):
- Hardware CWEs crowd into non-hardware assets, e.g. the hospital network interface
  (INF-Q2) returns `CWE-1051`, `CWE-1311`, `CWE-1315`. The `[Hardware design weakness]`
  marker and the missing domain filter are the likely causes (not isolated yet).
- Classic, broadly applicable entries (`CWE-306`, `CWE-798`) dropped out of several top-5 lists.
- Cloud backend (SDL-Q3) results are mixed (`CWE-1088` is a poor fit).

## Finding about the company document

The company document (section 2.5, T6) cites `CAPEC-189` for "key extraction via side-channel".
In CAPEC v3.9, `CAPEC-189` is **"Black Box Reverse Engineering"**; side-channel patterns are
e.g. `CAPEC-622` (Electromagnetic Side-Channel Attack). Worth confirming the intended
reference with the company/mentors.

## Not done / next steps

- No domain tags, filters, source quotas or reranking yet (needed to control the noise above).
- The T1-T6 ground-truth evaluation was not re-run on the full KB (it needs the live LLM).
- A new, relevance-labelled benchmark (labels over the full KB) is needed for a fair quality number.
- ISO/SAE 21434 and SESIP are still not in the KB (paid / terms unclear; need the company). CC, JIL and the CRA were loaded later (see addendum).
- MITRE EMB3D was not loaded (licence terms not checked).

## Addendum - free standards loaded (Compliance KB layer)

Stored in a separate table `standards_chunks` (same DB `trc_engine_fullkb`); `threat_patterns`
and Threat Agent retrieval are unaffected. Reference text only: **no mapping rules are encoded.**

| Document | Chunks |
|---|---:|
| Common Criteria CC:2022 R1, Parts 1-5 | 551 / 1,017 / 735 / 93 / 104 |
| CEM:2022 R1 | 1,907 |
| JIL Application of Attack Potential to Smartcards v3.2.1 | 221 |
| EU Cyber Resilience Act, Regulation (EU) 2024/2847 | 469 |
| **Total** | **5,097** |

Spot checks (cosine, MiniLM) returned the right material: CEM attack-potential tables for the
JIL/ISO-style factor query, CRA Art. 13/14 for vulnerability-handling, CC Part 3 AVA_VAN for
vulnerability analysis, JIL SPA/DPA sections for side-channel. These are 4 informal queries,
not a benchmark.

Not loaded: ISO/SAE 21434 (paid), SESIP (no stable direct link / reuse terms not stated),
IEC 62443 (paid). See `kb/NOTICE_STANDARDS.md`. Chunk locators are PDF page indexes, not printed page numbers.

Caveat on both KBs: the embedding model (MiniLM) reads roughly the first 256 tokens, so the
tail of the longest descriptions (up to 1,200 chars for MITRE entries) may not be embedded.
